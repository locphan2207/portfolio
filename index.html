Google Software Engineer · Current

  3. 03

    Monolith to normalised

    Split one overloaded table into a normalised schema in production, with no downtime and no broken consumers. A migration like this is barely about the SQL — it is sequencing, backfills, and dual writes held long enough that the old path is safe to delete.

    • Zero downtime
    • Backfill
    • Dual writes
  4. 04

    APIs over RPC

    Service contracts that stay stable while everything behind them moves. Versioning, backward compatibility and error semantics picked so the caller has an easy time — because the caller is another team, and their outage is my outage.

    • RPC
    • Protocol buffers
    • Versioning
  5. 05

    Trained, hosted, served

    A workflow that trains a model, hosts it, and answers live inference behind an endpoint. The interesting parts are the unglamorous ones: reproducible training runs, safe rollout, a latency budget, and a sane answer for when the model is wrong.

    • Python
    • Model serving
    • Live inference

    On the pager

    I am in the on-call rotation for the system my team maintains. Being the one who gets paged changes how you build: you write the runbook, you add the log line, you make failure legible at 3am. It is the fastest way I know to learn a system all the way down.

    • On-call

04 — About

Hardware major, software heart

I am a software engineer at Google. Before that I helped build a sportsbook from nothing, and before that I was studying hardware.

I graduated as a Computer Engineering major and learned to design embedded hardware systems — then kept picking up languages until software won. That background still shows up in how I work: understand the machine underneath, then build on it.

What has changed since the last version of this page is scale, and consequence. Working on something other teams depend on taught me to write the design doc before the code, to land a migration in stages instead of one heroic commit, to review carefully because somebody will be reading this in two years, and to carry the pager for what I ship. Most of the hard parts turned out not to be technical.

I also lean on AI heavily now — first drafts, unfamiliar APIs, the boilerplate, a review pass before I send code out. It has made me quick at the mechanical parts, which mostly buys me more time on the parts that are actually hard: deciding what to build, and what shape it should be.

    Full stack on a system my team owns end to end: the front end, the RPC services behind it, the schema underneath, and the ML serving on top. On call for it too.

  2. Smarkets Software Engineer

    A betting exchange. I worked on the sportsbook app and the services behind it — the mobile front end, a geofencing check, and the social features.
